# 프로젝트 삭제 기능 구현 계획

## 목표

프로젝트 설정에서 확인 절차를 거쳐 프로젝트와 선택한 삭제 범위의 데이터를 제거한다. 성공 시 Admin의 선택 상태와 캐시를 정리한다.

## 구현 단계

1. D1~D4를 사용자와 하나씩 결정하고 `03-decisions.md`에 기록한다.
2. 선택한 데이터 정책에 맞춰 서버의 `DELETE /api/v1/projects/{projectId}`와 서비스·저장소 삭제 순서를 구현한다.
3. D2가 에이전트 정리를 포함하면 Agent Graph에 프로젝트 단위 정리 요청과 PCM·저장소 스냅샷 정리를 구현하고 서버에서 호출한다.
4. Admin API 클라이언트와 React Query mutation을 추가하고, 프로젝트 설정에 위험 영역과 D3의 확인 UI를 구현한다.
5. D4에 따라 선택 프로젝트·localStorage·페이지를 갱신한다.
6. 서버 단위/컨트롤러 테스트, Agent 테스트(D2 선택 시), Admin typecheck·lint·build를 실행한다.
7. 결과와 검증 기록을 `04-result.md`에 남긴다.

## 결정 포인트

### D1. Spring 소유 데이터의 삭제 정책

- A. 프로젝트와 연관된 API 키, 레포지토리/자격 증명, 문서, Bugs, Issues, Issue-Bug 링크, 분석 결과, workflow runs, Issue branches를 함께 영구 삭제한다.
- B. 연관 데이터가 하나라도 있으면 삭제를 거절하고 먼저 수동 정리를 요구한다.
- C. 실제 삭제 대신 보관 상태로 전환한다.

**추천: A.** 사용자가 명시적으로 삭제를 요청했고 보관 기능은 범위 밖이다. 외래 키 관계를 안전한 순서로 지워야 하며, 복구할 수 없음을 UI에서 분명히 알린다.

### D2. Agent 소유 데이터와 실패 처리

- A. Agent Graph에 `project_deleted` 요청을 추가해 PCM 지식·검색 인덱스·프로젝트별 Git mirror/manifest를 지우고, 정리에 실패하면 Spring 프로젝트 삭제도 실패시킨다.
- B. Spring 소유 데이터만 삭제하고 Agent 데이터 정리는 이번 범위에서 제외한다.
- C. Spring 삭제를 먼저 완료하고 Agent 정리는 사후 최선 노력으로 수행한다.

**추천: A.** 데이터 소유 경계를 지키고 삭제 후 Agent에 민감한 프로젝트 자료가 남지 않게 한다. 현재 분산 트랜잭션/outbox는 없으므로, Agent 정리를 먼저 수행해 실패 시 사용자가 재시도할 수 있게 한다.

### D3. Admin 재확인 방식

- A. 삭제 대화상자에서 프로젝트 이름을 직접 입력해야 삭제 버튼을 활성화한다.
- B. 브라우저 확인창에서 한 번만 확인한다.

**추천: A.** Bugs와 분석 이력을 포함한 영구 삭제에 적합하며, 이름이 비슷한 프로젝트의 오삭제도 줄인다.

### D4. 삭제 성공 뒤 화면 상태

- A. 선택값을 비우고 리포트 화면의 프로젝트 미선택 상태로 이동한다.
- B. 남아 있는 첫 프로젝트를 자동 선택한다.
- C. 프로젝트 설정 화면에 머물러 프로젝트 미선택 상태를 표시한다.

**추천: A.** 다른 프로젝트를 사용자의 의도 없이 선택하지 않으며, 삭제 완료를 자연스럽게 확인할 수 있다.

## 공통 기준

- 존재하지 않는 프로젝트는 현재 API 관례대로 `404`를 반환한다.
- 삭제 성공 응답은 본문 없는 `204 No Content`로 한다.
- 요청 중에는 중복 삭제를 막고, 실패 시 프로젝트 선택과 데이터는 유지하며 오류를 표시한다.
- 기존 권한 체계를 변경하지 않는다.
