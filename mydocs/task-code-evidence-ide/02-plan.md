# 코드 근거 IDE 화면 개편 Plan

## 목표

분석 당시 고정 commit의 코드 근거를 파일 트리와 읽기 전용 코드 뷰로 제공한다. AI가 인용한 줄과 설명을 연결하고, 긴 파일은 필요한 문맥만 표시한다.

## 구현 단계

1. 분석 결과의 코드 citation 계약을 구조화하고, Agent Graph의 생성·품질 검증·저장 흐름을 보완한다.
2. Agent Graph에 snapshot 고정 파일 목록·부분 원문용 내부 읽기 계약을 추가한다.
3. Spring에 Issue·분석 결과 소유권을 검증한 외부 조회 API와 Agent 호출 adapter를 추가한다.
4. Admin에 IDE형 코드 근거 탭을 구현한다. 파일 트리, 선택 상태, 발췌 코드, 줄 번호, AI 하이라이트와 설명을 포함한다.
5. 계약·권한·경계 조건의 테스트와 Admin typecheck/lint를 수행한다.

## 결정 포인트

### D1. 파일 트리의 표시 범위

- A. 분석 citation이 있는 파일만 표시한다. 추천: 처음부터 관련 파일만 보여 탐색량과 조회 비용을 제한한다.
- B. 고정 snapshot의 모든 허용 파일을 표시한다. 근거 밖의 주변 코드를 탐색할 수 있지만 대형 저장소에서 UI와 API 비용이 커진다.

### D2. 파일 선택 시 코드 표시 범위

- A. citation 주변 발췌만 표시하고, 각 발췌 사이의 생략 구간을 명시한다. 추천: 긴 파일에서도 근거와 문맥을 빠르게 읽을 수 있다.
- B. 처음에는 발췌를 표시하고, 사용자가 요청하면 제한된 추가 줄 범위를 불러온다. 탐색성은 높지만 API·상태·보안 정책이 늘어난다.
- C. 선택 파일 전체를 표시한다. 구현은 단순하지만 대형 파일의 성능·가독성·노출 범위를 제어해야 한다.

### D3. 코드 citation의 필수 계약과 누락 처리

- A. 코드 근거는 `evidence_id`, repository ID, commit, 파일 경로, 시작·끝 줄, AI 설명을 필수로 하고, 품질 게이트가 snapshot과 줄 범위를 검증한다. 불완전한 항목은 코드 근거에서 제외하고 경고로 남긴다. 추천: UI 하이라이트의 정확성을 보장한다.
- B. 기존처럼 느슨한 citation도 보존하고 UI가 문자열 위치를 추정한다. 과거 결과는 많이 보이지만 잘못된 하이라이트 위험이 있다.

### D4. 기존 분석 결과의 호환 방식

- A. 구조화된 위치가 없는 기존 결과는 기존 카드형 근거 또는 "IDE 보기 불가" 안내로 표시하고, 새 분석부터 IDE 뷰를 보장한다. 추천: 저장된 immutable snapshot을 변경하지 않는다.
- B. 조회 시 기존 문자열 위치를 파싱해 IDE 뷰로 변환한다. 즉시 적용 범위는 넓지만 오해석과 예외 처리가 생긴다.

### D5. 저장소 조회 경계

- A. 브라우저는 Spring의 외부 API만 호출하고, Spring이 Agent Graph의 읽기 전용 내부 계약을 호출한다. 추천: 프로젝트·이슈·분석 결과 권한과 snapshot 검증을 Spring 소유 경계에 둔다.
- B. Admin이 Agent Graph를 직접 호출한다. 구현 경로는 짧지만 현재 소유권·API 경계 원칙을 위반한다.

## 예상 API와 데이터 흐름

Admin → Spring 외부 API → Agent Graph 내부 읽기 API → 고정 repository mirror

Spring은 최신 분석 snapshot에서 repository ID·commit·허용 파일을 확인하고, Agent에는 해당 분석의 고정 snapshot만 조회하도록 요청한다. Agent는 비밀 경로를 제외하고 줄 범위와 최대 응답 크기를 제한한다.

## 검증 기준

- 코드 citation이 고정 snapshot의 실제 파일과 유효한 줄 범위를 가리킨다.
- 다른 프로젝트·이슈·commit의 파일을 조회할 수 없다.
- 긴 파일은 선택한 citation 주변 문맥과 생략 구간을 표시한다.
- 하나의 파일의 여러 citation이 모두 구분되어 하이라이트된다.
- 기존 분석 결과는 D4에서 선택한 방식으로 안전하게 처리된다.
