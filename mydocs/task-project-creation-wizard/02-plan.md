# 프로젝트 생성 마법사 구현 계획

## 목표

프로젝트 추가를 넓은 단계형 화면으로 전환하고, 기본 정보부터 분석 준비 설정까지 한 흐름에서 완료한다.
기존 API 계약은 유지한다.

## 구현 단계

### 1. 생성 화면 진입 구조

- App의 화면 상태에 프로젝트 생성 화면을 추가한다.
- 사이드바의 `프로젝트 추가`가 생성 화면으로 이동하도록 이벤트 계약을 변경한다.
- 생성 취소와 완료 후 이동 경로를 연결한다.
- 관련 Storybook 스토리를 새 계약에 맞춘다.

### 2. 마법사 골격과 기본 정보

- 넓은 콘텐츠 영역, 단계 표시기, 이전·다음·취소 버튼을 구현한다.
- 프로젝트 이름과 설명 입력, 길이 제한, 필수값 검증을 제공한다.
- 단계 이동 시 입력 상태를 유지한다.

### 3. 저장소와 참고 문서 단계

- 저장소 입력과 검증을 생성 흐름에 맞게 구성한다.
- PDF·Markdown 파일 선택, 제목 수정, 대기 목록 관리를 제공한다.
- 선택 설정은 결정된 정책에 따라 건너뛸 수 있게 한다.

### 4. 검토, API 실행, 실패 복구

- 제출 전에 기본 정보, 저장소, 문서 목록을 요약한다.
- 프로젝트 생성 후 선택한 후속 설정 API를 순서대로 실행한다.
- 진행 상태와 성공·실패 항목을 표시하고 정해진 복구 동작을 제공한다.
- 성공한 프로젝트를 현재 프로젝트로 선택한다.

### 5. 문서화와 검증

- `API_UI_CHANGES.md`에 생성 흐름 변경을 기록한다.
- 주요 단계와 상태를 Storybook에서 확인할 수 있게 한다.
- `npm run typecheck`, `npm run lint`, `npm run build`를 실행한다.
- 결정과 결과를 `03-decisions.md`, `04-result.md`에 기록한다.

## 결정 포인트

### D1. 화면 표시 방식

- A: App 본문 전체를 사용하는 독립 화면
- B: 현재 화면 위에 넓은 전체 화면 모달 표시
- C: 오른쪽 대형 패널 표시
- 추천: A. 브라우저 크기에 자연스럽게 대응하고 단계가 늘어나도 공간과 탐색 구조가 안정적이다.

### D2. 단계 구성

- A: `기본 정보 → 저장소 → 문서 → 검토·생성` 4단계
- B: `기본 정보 → 분석 설정(저장소·문서) → 검토·생성` 3단계
- C: `기본 정보 → 저장소 → 문서 → 검토 → 완료` 5단계
- 추천: A. 입력 성격이 다른 저장소와 문서를 분리하면서 완료 결과는 제출 단계 안에서 자연스럽게 전환할 수 있다.

### D3. 프로젝트를 서버에 생성하는 시점

- A: 마지막 검토에서 생성하고 후속 설정을 순차 실행
- B: 기본 정보 단계를 통과할 때 먼저 생성하고 이후 설정을 즉시 저장
- 추천: A. 중간 취소로 이름뿐인 프로젝트가 남는 일을 줄이고, 마지막 전까지 이전 단계 편집이 자유롭다.

### D4. 저장소와 문서의 필수 여부

- A: 둘 다 선택 사항으로 두고 건너뛰기 허용
- B: 저장소 하나는 필수, 문서는 선택 사항
- C: 둘 다 필수
- 추천: A. 문서 분석이나 수동 버그 수집처럼 저장소 없이 시작할 사용 사례를 막지 않는다.

### D5. 최초 생성에서 지원할 연결 개수

- A: 저장소 최대 1개, 문서 여러 개
- B: 저장소와 문서 모두 여러 개
- C: 저장소와 문서 모두 최대 1개
- 추천: A. 일반적인 첫 설정은 간결하게 유지하고 추가 저장소는 기존 설정 화면에서 연결할 수 있다.

### D6. 후속 설정 일부 실패 처리

- A: 생성된 프로젝트는 유지하고 실패 항목 재시도 또는 설정 화면 이동 제공
- B: 하나라도 실패하면 생성된 프로젝트를 자동 삭제하고 처음부터 재시작
- C: 프로젝트는 유지하지만 마법사를 즉시 닫고 오류만 알림
- 추천: A. 성공한 업로드와 저장소 요청을 보존하고, 자동 삭제에 따른 데이터 손실 위험을 피한다.

### D7. 완료 후 기본 이동 위치

- A: 새 프로젝트의 버그 리포트 화면
- B: 새 프로젝트의 설정 화면
- C: 사용자가 완료 화면에서 목적지를 선택
- 추천: A. 프로젝트 생성의 기본 목적지로 이동하고, 설정 보완은 사이드바에서 접근할 수 있다.

### D8. 작성 중 취소 정책

- A: 입력이 있으면 확인 대화상자를 표시하고, 없으면 즉시 종료
- B: 항상 즉시 종료
- C: 입력을 브라우저에 임시 저장해 다음 진입 때 복원
- 추천: A. 실수로 입력을 잃는 일을 막으면서 별도 초안 수명 주기를 만들지 않는다.

### D9. 기존 설정 입력 UI와의 코드 관계

- A: 공통 입력 컴포넌트를 추출해 마법사와 설정 화면이 공유
- B: 마법사 전용 컴포넌트를 만들고 기존 화면은 유지
- 추천: B. 기존 화면 회귀 범위를 제한하고, 실제 중복이 안정된 뒤 별도 리팩터링할 수 있다.

2. D2 단계 구성

4. D4 선택 설정 필수 여부
5. D5 최초 연결 개수
6. D6 일부 실패 처리
7. D7 완료 후 이동 위치
8. D8 취소 정책

각 결정을 사용자에게 하나씩 확인하고 `03-decisions.md`에 근거와 함께 기록한다. 결정에 따른 구현을
작은 단위로 커밋하며, 아직 결정되지 않은 항목은 구현하지 않는다.

## 검증 기준

- 각 단계의 이전·다음 이동과 입력 유지
- 필수값, URL, 파일 형식 검증
- 선택 단계 건너뛰기
- 프로젝트 생성과 후속 API 성공·부분 실패 상태
- 생성 완료 후 프로젝트 선택과 화면 이동
- 취소 시 입력 손실 방지
- 데스크톱·모바일 레이아웃과 키보드 접근
- TypeScript, ESLint, production build 통과
